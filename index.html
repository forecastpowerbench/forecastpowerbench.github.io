ForecastPowerBench is a workload-aware benchmark for studying the inference efficiency of time series foundation models (TSFMs). It examines how context length, forecast horizon, batch size, model architecture, and hardware shape throughput, energy consumption, and memory requirements.

Overview

Accuracy alone does not tell the whole story

Forecasting accuracy is only one part of deployment suitability. ForecastPowerBench evaluates 10 time-series foundation models across four NVIDIA platforms, measuring how context length, forecast horizon, batch size, and hardware affect inference throughput, energy per forecast, memory use, and feasibility.

01

Workload-aware evaluation

Vary context length, forecast horizon, and batch size to expose how inference behavior changes across forecasting workloads.

02

Efficiency beyond throughput

Consider throughput, energy per forecast, and peak memory together rather than treating speed as the only deployment criterion.

03

Across hardware platforms

Compare model behavior on a high-end accelerator, workstation GPUs, and an edge platform, while accounting for platform-specific constraints.

Metrics

What ForecastPowerBench measures

ForecastPowerBench combines software-instrumented inference measurements with GPU-device telemetry. Throughput and timing are measured around the benchmark execution path; energy is reported from the GPU power domain only, not as whole-machine or wall-plug energy.

ThroughputForecast windows processed per second; optionally report forecast points per second.
Energy per Forecast (EPF)GPU-reported energy during the measurement interval divided by the number of forecast windows completed.
Peak memoryMaximum observed memory use within the documented measurement scope.
GPU powerPower telemetry from the GPU-reported measurement domain; it is not a measurement of total system power.
Energy measurement scope. The current benchmark reports GPU-domain energy from software-accessible device telemetry. It does not measure CPU energy, display, storage, fans, peripherals, or total system/wall-plug energy. GPU power readings should not be interpreted as whole-machine energy consumption.

Energy per Forecast

EPF is the GPU-reported energy consumed during the timed inference interval, normalized by the number of forecast windows completed in that interval.

\[\mathrm{EPF}\ [\mathrm{J/forecast}] = \frac{E_{\mathrm{GPU}}}{N_{\mathrm{forecast}}}\]

Fair comparisons

Record the workload configuration, warm-up policy, measurement duration, repeat identifiers, power mode, telemetry scope, and run status. Report variability across repeated measurements.

Measurement protocol

How each inference run is measured

Each run fixes a model, GPU, context length, forecast horizon, and batch size. Two warm-up rounds are excluded, then five measurement rounds of 300 inference batches each are timed while GPU telemetry is sampled.

GPU
Energy boundary: GPU device only

GPU energy is derived from NVML power telemetry. CPU energy, DRAM, storage, fans, peripherals, and wall-plug energy are excluded. CPU/process memory is reported separately.

01

Configure

Select model, GPU, context length, horizon, and batch size.

02

Warm up

Run two warm-up rounds (CUDA/JIT initialization); they are excluded from all metrics.

03

Measure

Run five measurement rounds of 300 inference batches each, counting completed forecasts and sampling GPU telemetry.

04

Aggregate

Aggregate across the five rounds to report throughput, EPF, and peak memory.

Software counters

Each model runs with its native implementation and author-recommended inference procedure. Timing and energy cover only the forecasting phase; model-specific preprocessing and input construction are excluded. Elapsed time and completed forecasts are recorded for each round.

Concurrent telemetry

NVML samples GPU power, memory, GPU and SM utilization, clock frequency, and temperature every 50 ms. GPU energy is obtained by integrating the sampled power trace with the trapezoidal rule. psutil records CPU/process memory. Only GPU power contributes to EPF.

Performance

Throughput

\[T = \frac{N_{\mathrm{forecast}}}{t_1 - t_w}\]

Completed forecast windows \(N_{\mathrm{forecast}}\) per second over the measured interval \([t_w, t_1]\), in forecasts/s.

GPU energy

Energy per Forecast

\[\mathrm{EPF} = \frac{1}{N_{\mathrm{forecast}}}\int_{t_w}^{t_1} P_{\mathrm{GPU}}(t)\,dt\]

GPU energy \(E_{\mathrm{GPU}}\), the trapezoidal integral of GPU power \(P_{\mathrm{GPU}}\) sampled every 50 ms, divided by completed forecasts. Reported in J/forecast.

Memory

Peak GPU memory

\[M_{\mathrm{peak}} = \max_{t \in [t_w,\,t_1]} M_{\mathrm{GPU}}(t)\]

Maximum observed GPU memory during the measured inference interval, in GB.

Interpretation boundary. These measurements describe inference software performance and GPU-device energy, not total machine energy.

Warm-up settings, repeat IDs, completion status, OOM/error counts, throttling flags, telemetry sample counts, and aggregate statistics are retained where available.

Key findings

What the experiments reveal

01

Workload scaling is model-dependent

Increasing context length generally reduces throughput, but the magnitude varies widely. Longer horizons cause sharp degradation for some models, while others remain comparatively stable. Performance at a single workload configuration is therefore not enough to characterize deployment behavior.

02

Smaller models are not necessarily faster or more efficient

Models with fewer parameters do not consistently achieve higher throughput or lower EPF, and models in the same architectural family can have very different system costs. Model size and architecture labels are no substitute for measuring throughput and energy under representative workloads.

03

Accuracy–efficiency trade-offs depend on the forecasting regime

No single model is optimal across all workloads. The Pareto-optimal models change with the regime: Moirai-2 and Kairos for Short, TTM-R3, Sundial, and Chronos-2 for Medium, and TTM-R3 and Chronos-2 for Long.

04

Hardware shapes efficiency and operating points

Broad scaling trends often persist across platforms, but absolute throughput, EPF, and feasible operating points vary with hardware, and some models cannot run the largest workloads within device memory. A configuration that performs well on a cloud GPU may not stay optimal on workstation or edge hardware.

Key takeaway: batching generally improves throughput and reduces EPF until model- and hardware-dependent saturation points. These gains are not uniform, and absolute performance and feasible workloads differ across platforms.
